	\section{Priority Assignments Optimization}
    \label{section_priority_opt}

    This section addresses the \emph{priority-assignment subproblem}: given a task set $\boldsymbol{\tau}$ operating under environment $\textbf{E}_k$ with the QoS budgets $\boldsymbol{\mathcal{Q}}$ held \emph{fixed}, find the priority assignment $\boldsymbol{P}$ that maximizes $\textbf{SP}(\boldsymbol{P}; \textbf{E}_k)$ subject to the important-task constraint~\eqref{eq_important_task_constraint}.
    That is, throughout this section we solve only for the priority assignment $\boldsymbol{P}$ in~\eqref{eq_overall_obj}; Section~\ref{section_config_opt} lifts the QoS-fixed restriction and optimizes the priority assignment $\boldsymbol{P}$ and the QoS budgets $\boldsymbol{\mathcal{Q}}$ jointly.

    Priority assignment is a fundamental and influential scheduling technique, particularly in real-time systems, where effective scheduling ensures strong performance guarantees.
    Such guarantees are crucial in robotics applications, including autonomous driving and aerospace systems.
    However, designing an efficient online optimization algorithm is hard due to stringent run-time complexity requirements: even a single evaluation of the SP metric requires going through all tasks and therefore has at least linear complexity, not to mention performing further optimization.
    We therefore design an efficient incremental optimization algorithm that trades off optimality for better run-time efficiency.

    To simplify the presentation, we first describe a brute-force algorithm for priority assignments.
    We then propose improvements inspired by the classical Audsley’s algorithm~\cite{Audsley91optimalpriority} and introduce incremental optimization techniques to balance computational speed and performance.


	\subsection{Brute-Force Priority Assignments}
	\label{section_bf_pa}
    Given a task set of $n$ tasks, the brute-force algorithm enumerates and evaluates all $n!$ possible priority assignment vectors to identify the optimal solution.
    The brute-force algorithm is optimal by construction, and we use it as an offline optimality reference in our experiments (Section~\ref{section: simulation}).
    While straightforward, this approach has significant computational limitations.
    As the number of tasks increases, the factorial growth of possible assignments leads to prohibitive computation costs.
    This makes brute-force methods impractical for online use, particularly in embedded systems where resource constraints and real-time demands are prevalent.


	\subsection{Optimize Safety Based on Audsley's Algorithm and Beam Search}
	\label{section_audsley_pa}
    Maximizing the SP metric is closely related to maximizing the overall system's schedulability.
    When the QoS budgets are fixed, the performance function in the SP metric~\eqref{eq_sp_def} becomes a constant coefficient.
    This motivates us to leverage optimal priority assignment algorithms to optimize the SP metric.
    Among various options, Audsley's algorithm~\cite{Audsley91optimalpriority} stands out due to its $O(n^2)$ runtime complexity, where $n$ is the number of tasks in the task set.

    The core idea of Audsley's algorithm is straightforward: in each iteration, the algorithm identifies tasks from a candidate pool (\ie, tasks that have not been assigned priorities yet) that can tolerate the lowest priority while still meeting their deadlines.
    If such a task is found, its priority is assigned; otherwise, the algorithm concludes that the task set is not schedulable.
    Under certain conditions~\cite{Audsley91optimalpriority}, this approach is optimal for maximizing schedulability (note: optimal for schedulability, not for the SP metric).


    	However, several issues prevent direct application of Audsley's algorithm in our case:
    \begin{itemize}
        \item Schedulability Only: Audsley's algorithm is designed to maximize system schedulability but does not explicitly optimize the SP metric.
        Priority assignments found by the algorithm may not yield the best SP metric.
        \item Soft real-time considerations: The original algorithm assumes hard real-time constraints.
        In contrast, we target soft real-time systems, where priority assignments considered ``unacceptable'' by Audsley's algorithm may still be valuable.
    \end{itemize}

    To address these limitations, we propose to modify Audsley's algorithm based on beam search to optimize the SP metric.
    The modified algorithm retains Audsley's iterative structure but incorporates additional mechanisms to evaluate and prioritize assignments based on SP metric performance.

    The modified algorithm works iteratively.
    Each partial priority assignment $p$ carries its own pool of not-yet-assigned tasks; assigning a task to $p$ appends it at the current priority level and removes it from that pool.
    In the \ith{k} iteration, the algorithm identifies the task to assign the \ith{k} lowest priority.
    The key steps within each iteration are:
\begin{itemize}
    \item For each recorded partial priority assignment vector $p$ (the set $\partialpa$ in Algorithm~\ref{alg:modified_audsley}), evaluate the accumulated SP-value loss incurred by the tasks already placed in $p$.
    \item For each $p$, for each task $\tau_i$ still in $p$'s pool, form a copy of $p$, assign $\tau_i$ the \ith{k} lowest priority, and compute the SP metric loss associated with $\tau_i$.
    \item Retain the top-$m$ ($m>0$ is the beam width) partial priority assignment vectors with the \emph{lowest} accumulated SP loss.
    These candidates are passed to the next iteration.
\end{itemize}

This heuristic-based modification allows the algorithm to balance schedulability with SP metric optimization.
The pseudocode for the modified Audsley's algorithm is shown below:

	\begin{algorithm}[htbp]
		\caption{Modified Audsley's Algorithm} \label{alg:modified_audsley}
		\KwIn{Task set $\boldsymbol{\tau}$, beam width $m$}
		\KwOut{Selected priority assignment}
		$\partialpa = \{$ a single empty partial path $p$ with $p.\textsc{Pool} \leftarrow \boldsymbol{\tau}$ $\}$ \tcp{lowest-priority task appended first}
		\For{$k$ in $0,...,N-1$}
		{
			$\partialpacur=\{\emptyset\}$\\
			\For{$p$ in $\partialpa$}{
				\For{$\tau_i$ in $p.\textsc{Pool}$}{
					$p' \leftarrow \textbf{copy}(p)$ \tcp{copy before extending}
					$p'.\textsc{Assign}(\tau_i)$ \tcp{append $\tau_i$ at priority $k$; remove $\tau_i$ from $p'.\textsc{Pool}$; accumulate SP loss}
					$\partialpacur.\textbf{Push}(p')$\\
				}
			}
			$\partialpa = \textbf{SelectTop}(\partialpacur, m)$ \tcp{keep the $m$ paths of \emph{lowest} accumulated SP loss}
		}
		\KwRet $\textbf{SelectTop}(\partialpa, 1)$
	\end{algorithm}

	\begin{Example}
        Consider a task set of three tasks: $\tau_0$, $\tau_1$, and $\tau_2$.
        Assume we retain two partial priority assignment vectors during each iteration.

        First iteration.
        Assign the lowest priority to each task and evaluate the SP loss.
        Suppose $\tau_0$ and $\tau_1$ have the smallest SP loss.
        The retained partial priority assignments are:
        \begin{itemize}
        \item $P_0$: $\{\tau_0 \}$.
        \item $P_1$: $\{\tau_1 \}$.
        \end{itemize}

        Second iteration.
        For each retained partial priority assignment, assign the second-lowest priority to the remaining tasks and evaluate the accumulated SP loss:
        \begin{itemize}
            \item $P_2: \{\tau_0, \tau_1\} = 0.5$
            \item $P_3: \{\tau_0, \tau_2\} = 0.4$
            \item $P_4: \{\tau_1, \tau_0\} = 0.6$
            \item $P_5: \{\tau_1, \tau_2\} = 0.8$
        \end{itemize}
        Therefore, the two partial priority assignments to keep after the second iteration are $P_2$ and $P_3$.

        Third iteration.
        Assign the third-lowest priority to the remaining task for each retained assignment:
        \begin{itemize}
            \item $P_6:  \{\tau_0, \tau_1, \tau_2\}$
            \item $P_7:  \{\tau_0, \tau_2, \tau_1\}$
        \end{itemize}
        Evaluate the SP loss for these two assignments and return the one with the minimum SP loss as the final solution.
	\end{Example}


	\subsection{Incremental Priority Assignment Optimization}
	\label{section_increment_pa}

    Incremental optimization can further accelerate the priority assignment process by leveraging the observation that, between consecutive re-optimization intervals, typically only a small number of tasks' execution time distributions change significantly.
    Additionally, not all tasks' execution time distributions vary significantly across environments or over time.

    The incremental search is seeded from a Deadline-Monotonic priority assignment in which every important task is locked above every non-important task (the important-first group lock of Section~\ref{eq_safety}).
    Starting from this seed, when performing priority assignments, we identify tasks with significant changes in execution time distribution and re-search each such task's priority position over one half of the priority range, adopting the best position found.
    For all other tasks, we retain their \textit{relative} priority assignments, as their execution time distributions remain unchanged, and thus their optimal relative priorities are likely to remain the same.
    If multiple tasks experience significant changes, this adjustment is applied individually to each task.


Let $\tau_i$ represent a task whose execution time distribution changes significantly.
The direction of $\tau_i$'s priority re-search is categorized based on two factors: whether $\tau_i$ holds the uniquely highest SP weight $w_i$ in the task set~\eqref{eq_sp_def}, and whether $\tau_i$'s execution time increases or decreases.
The four possible scenarios are:
\begin{enumerate}
    \item If $\tau_i$ has the uniquely highest weight and its execution time increases, the re-search direction is \emph{upward}: scan positions of higher priority than $\tau_i$'s current one.
    \item If $\tau_i$ has the uniquely highest weight and its execution time decreases, the re-search direction is \emph{downward}: scan positions of lower priority.
    \item If $\tau_i$ does not have the uniquely highest weight and its execution time increases, the re-search direction is \emph{downward}.
    \item If $\tau_i$ does not have the uniquely highest weight and its execution time decreases, the re-search direction is \emph{upward}.
\end{enumerate}
In every scenario $\tau_i$ is removed from the current priority vector and re-inserted at each position within the chosen half; the position yielding the highest SP metric is adopted if it strictly improves on the current assignment, otherwise the current position is retained.
Potential issues in terms of optimal solution drift caused by the incremental optimization is discussed in Section~\ref{sec: drift}.


	\subsection{RTA Cache: Reusing Response-Time Computation}
	\label{section_rta_cache}

    Both the modified Audsley search (Section~\ref{section_audsley_pa}) and the incremental adjustment above evaluate the SP metric many times per interval, and a single evaluation already requires a response-time analysis (RTA) over all tasks.
    Recomputing RTA from scratch for every candidate is too costly for online use.
    The RTA cache makes incremental optimization practical by reusing prior computation whenever a candidate differs only slightly from one already scored.

    \textbf{Champion and the single-change condition.}
    The cache holds a \emph{champion}: a priority assignment together with the full per-task response-time distributions $\rtDist{i}$ it induces.
    A candidate is served from the cache only if it differs from the champion by \emph{at most one task}---the single-change invariant, $|\mathrm{diff}| \leq 1$.
    Relative to the champion, a candidate may change the execution-time distribution $\extDist{m}$ of at most one task $\tau_m$, the priority position of at most one task $\tau_m$ on its core, or both; when both change they must concern the \emph{same} task on the \emph{same} core (a combined execution-time and priority change counts as one).
    Any broader change---two tasks' execution times, a task migrating to another core, two independent priority moves, or an execution-time change on one task paired with a priority move of another---violates the invariant ($|\mathrm{diff}| > 1$) and is rejected by a single-change check.
    When candidate and champion are identical ($|\mathrm{diff}| = 0$), every $\rtDist{i}$ is reused unchanged.

    \textbf{Which response times can be reused.}
    We now state precisely which $\rtDist{i}$ the cache reuses.
    Let $\boldsymbol{\tau}$ be the champion task set with per-task response-time distributions $\rtDist{i}$, and let $\boldsymbol{\tau}^{m}$ denote the candidate obtained by changing a single task $\tau_m$ on core $c$ (its execution-time distribution and/or its priority position); $\rtDistCand{i}$ denotes $\tau_i$'s response-time distribution under $\boldsymbol{\tau}^{m}$.
    Number priority positions on each core from highest ($0$) to lowest, and let $\tau_m$ move from $\mathit{old\_pos}$ to $\mathit{new\_pos}$ on core $c$ (equal for an execution-time-only change), with $p_{\min}=\min(\mathit{old\_pos},\mathit{new\_pos})$ and $p_{\max}=\max(\mathit{old\_pos},\mathit{new\_pos})$.
    Throughout, $hp(i)$ is the set of tasks with strictly higher priority than $\tau_i$ on the \emph{same} core, and we rely on the fixed-priority scheduling property that $\rtDist{i}$ depends only on $\tau_i$'s own execution-time distribution $\extDist{i}$ and on the execution-time distributions, periods, and membership of $hp(i)$---never on lower-priority tasks or on the order within $hp(i)$.

    \begin{observation}[Cross-core reuse]
    \label{obs:rta_cross_core}
    If $\tau_i$ is not on core $c$, then $\rtDistCand{i} = \rtDist{i}$.
    \end{observation}
    \noindent\textit{Proof.}
    Under partitioned scheduling, $hp(i)$ contains only tasks on $\tau_i$'s own core, so neither $\tau_m$'s execution-time distribution nor its priority position on core $c$ enters $\tau_i$'s response-time computation~\eqref{eq_prob_rta}.
    Hence $\rtDistCand{i}=\rtDist{i}$, and the champion $\rtDist{i}$ is reused verbatim. \hfill$\square$

    \begin{lemma}[Execution-time change]
    \label{lem:rta_et_change}
    Suppose the candidate differs from the champion only in $\tau_m$'s execution-time distribution (possibly together with a priority move of $\tau_m$ on core $c$).
    Then on core $c$, every task at position $< p_{\min}$ satisfies $\rtDistCand{i} = \rtDist{i}$ (bit-identical); every task at position $\geq p_{\min}$ must be recomputed.
    \end{lemma}
    \noindent\textit{Proof.}
    For a task $\tau_i$ at position $< p_{\min}$, $\tau_m$ sits at position $\geq p_{\min}$ in both the champion and the candidate, so $\tau_m \notin hp(i)$ in both and $\tau_i \neq \tau_m$; $\tau_i$'s own execution-time distribution and the membership, execution-time distributions, and order of $hp(i)$ are all unchanged.
    By the fixed-priority property, $\rtDist{i}$ is determined solely by these quantities, so $\rtDistCand{i}=\rtDist{i}$.
    For a task at position $\geq p_{\min}$, either $\tau_i = \tau_m$ (its own execution-time distribution changed) or $\tau_m \in hp(i)$ with a changed execution-time distribution, so $\rtDistCand{i} \neq \rtDist{i}$ and the distribution is recomputed. \hfill$\square$

    \begin{lemma}[Pure priority move]
    \label{lem:rta_priority_move}
    Suppose the candidate differs from the champion only by moving $\tau_m$ from $\mathit{old\_pos}$ to $\mathit{new\_pos}$ on core $c$, with all execution-time distributions unchanged.
    Then on core $c$:
    \begin{enumerate}
        \item position $< p_{\min}$: $\rtDistCand{i} = \rtDist{i}$ (bit-identical);
        \item $p_{\min} \leq \text{position} \leq p_{\max}$: recompute;
        \item position $> p_{\max}$: $\rtDistCand{i} = \rtDist{i}$ in the lossless analysis, and the cached $\rtDist{i}$ is a safe upper bound on $\rtDistCand{i}$ under the implementation's conservative compression.
    \end{enumerate}
    \end{lemma}
    \noindent\textit{Proof.}
    \emph{(1)} For $\tau_i$ at position $< p_{\min}$, $\tau_m$ is below $\tau_i$ in both orderings, so $\tau_m \notin hp(i)$ in both; $hp(i)$ is unchanged in membership, execution-time distributions, and order, giving $\rtDistCand{i}=\rtDist{i}$.
    \emph{(2)} For $\tau_i$ inside $[p_{\min},p_{\max}]$, $\tau_m$ crosses $\tau_i$, so the membership of $hp(i)$ differs between champion and candidate; $\rtDistCand{i}$ is recomputed.
    \emph{(3)} For $\tau_i$ at position $> p_{\max}$, $\tau_m \in hp(i)$ in both orderings (at $\mathit{old\_pos} \leq p_{\max}$ and $\mathit{new\_pos} \leq p_{\max}$, both below $\tau_i$) with the same execution-time distribution; the \emph{set} $hp(i)$ is identical and only the order within $[p_{\min},p_{\max}]$ is permuted.
    The response-time computation~\eqref{eq_prob_rta} forms $\rtDist{i}$ by convolving $\extDist{i}$ with the execution-time distributions $\{\extDist{j} : \tau_j \in hp(i)\}$ and iteratively folding in each higher-priority task's interference, which is governed by that task's period $T_j$ alone; convolution is commutative, and the interference of each $\tau_j \in hp(i)$ depends only on $\extDist{j}$ and $T_j$, not on the order within $hp(i)$. Hence the lossless $\rtDistCand{i}=\rtDist{i}$.
    The implementation interleaves lossy compression steps that are stochastically conservative---probability mass is only moved to later (larger) response-time values---so the order-dependent cached $\rtDist{i}$ stochastically dominates the true $\rtDistCand{i}$; reusing $\rtDist{i}$ therefore never underestimates the deadline-miss probability. \hfill$\square$

    In both lemmas the recomputed tasks form a contiguous range on a single core, so an incremental evaluation touches only a slice of one core rather than all $N$ tasks.

    \textbf{Interface.}
    The cache exposes three operations:
    \begin{itemize}
        \item \textsc{Initialize} performs a full RTA and establishes the champion, used at the start of each interval where the carried assignment may differ from the previous champion by more than one task.
        \item \textsc{Evaluate} patches a candidate that satisfies $|\mathrm{diff}| \leq 1$ against the champion and returns its $\rtDist{i}$, reusing the champion's per-task computation; it does not modify the champion.
        \item \textsc{AdoptChampion} commits a candidate (with its already-computed $\rtDist{i}$) as the new champion, so that subsequent candidates are compared against it and the single-change invariant is preserved across successive moves.
    \end{itemize}

    The collaborative PA+QoS loop of Section~\ref{section_config_opt} is structured around this invariant---every step changes exactly one task, so every evaluation reuses the cache.
    Implementation details (per-core higher-priority-prefix checkpoints and the per-task reuse classification) are deferred to Section~\ref{section_implementation}.

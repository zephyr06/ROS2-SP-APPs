# Sketch — Priority Assignment & Task-Config (TL) Optimization (PW.1.2)

> Code-side truth for priority-assignment methods + TL (task-config) optimization.

## TL;DR
- **PA = three modes:** (a) brute force `n!` (`OptimizePA_BF`); (b) modified Audsley + beam (`OptimizePA_Incre::OptimizeFromScratch`) — a **heuristic**, NOT optimal/exhaustive; (c) incremental single-task re-search (`OptimizeIncre_SingleTask`), the online path.
- **TL optimization = coordinate descent over the per-task TL grid**, patience-bounded outward walk (NOT radius-capped). Complexity `M^N → O(M·N)`.
- **Env-task reframing:** TL-optimizable tasks use the *same* incremental primitive as env-changed tasks (one merged E+L queue) via `OptimizeIncreSingleTask`.
- **⚠ Draft drift:** `‖λ−λ^(k)‖≤δ` / "3 candidates" (`eq: incremental_configuration`, section8/section9) is **STALE** — production walks the *full* grid bounded by `patience`, not δ. (§4.)

## 1. Priority assignment — three modes

**1a. Brute force — `n!` enumeration.** `OptimizePA_BF`/`IterateAllPAs`: depth-N recursion (depth `start`: try each not-yet-assigned task `i`, append, recurse, backtrack; at `start==N` score via `EvaluateSPWithPriorityVec`, keep max), polled against shared budget `BFSharedBudgetCancelled` (P1.14 cross-leaf timeout). **Why:** optimality at small N (offline/reference solver). SP non-monotone in ordering → no greedy sort is correct → search required; `n!` is the ground truth the heuristics are checked against. Intractable as N grows → 1b/1c.

**1b. Modified Audsley + beam — heuristic, NOT "optimal".** `OptimizeFromScratch(K)`, `K=Layer_Node_During_Incremental_Optimization=2`: **modified Audsley** + **beam width K**. Audsley structure: assign **lowest-first** — iterate `curr_priority` 0→N−1; at each level extend each surviving partial path by one task at that level. Beam: `priority_queue<PriorityPartialPath,…,CompPriorityPath>` keeps only **K best** partial paths per level. Partial-path cost (`PriorityPartialPath::UpdateSP`): for the just-assigned (lowest-pri) task, RTA vs already-assigned (higher-pri) tasks + add *lost* SP (`sp_lost += effective_weight − sp_cur`, `effective_weight=weight*perf_coefficient`); comparator ranks `sp_lost` asc (smaller loss first), tie weight desc then min-ET asc (assign low pri to low-weight/long-ET tasks). Final: `res=partial_paths[0].pa_vec_lower_pri` reversed; `opt_sp_` re-scored exactly via `EvaluateSPWithPriorityVec` (accumulated `sp_lost` is an approximation). **Why:** SP non-monotone → single greedy pass unsound, full `n!` intractable online. Audsley+beam keeps **O(K·N²)** RTA evals. **Heuristic:** the beam prunes non-top-K paths → **not guaranteed optimal** (a pruned path could lead to the optimum). Paper must say "heuristic," never "optimal"/"exhaustive." Interval-0/reopt bootstrap (`ReOptimizePeriodic`→`RunIntervalDescent(Reopt)`→`CallOptimizerGivenTimeLimits(from_scratch=true)`→`OptimizeFromScratch`).

**1c. Incremental — single-task re-search (online path).** `OptimizeIncre(dag_tasks_update)`: per-interval online entry; assumes carried PA (`opt_pa_`, warm-started) is near-optimal, only ET-changed tasks need re-search. (1) **Diff:** `FindTaskWithDifferentEt` → one `DiffObj{task_id,increase}` per task whose `execution_time_dist !=` old (`FiniteDist::operator!=`, 10%-relative approx_equal); `increase`=avg ET up. (2) **Baseline re-score:** re-score carried PA under new env (`rta_cache->Initialize`+`ObtainSP_Full_From_NodeRTAs`→`opt_sp_`; cache always engaged — nullopt builds a local `RTACache`, bit-identical to former oracle). (3) **Per-task 1D re-search:** for each `DiffObj`, `OptimizeIncre_SingleTask`: `FindPriorityVec1D_Variations` → `RemoveOneTask` then re-insert at each pos in **one half** of the order; `AnalyzePriorityChangeStatus` picks the half (ET-up+highest-weight→`Increase`; ET-up+not→`Decrease`; symmetric for ET-down); carried pos skipped (`exclude_opt_pa=true`); each variation scored via cache, adopt on strict `>`, `AdoptChampion` advances champion so next variation stays `|diff|≤1`. (4) Advance `dag_tasks_=dag_tasks_update`. **Why:** dynamic env → typically one task's ET changed per interval (env-dep sparse, `ENV_DEPENDENT_TASKS_RATIO∈[0.1,0.3]`); re-running `n!`/beam would blow latency → re-search only the changed task's 1D position (≤N−1 candidates, one half), reusing carried PA elsewhere → bounded online cost. **1-task-ET-diff property (`\agent` theorem question):** the single-change invariant `|diff|≤1` is *enforced structurally*, not assumed — `RTACache::Evaluate` serves only `|diff|≤1` and **throws** on `|diff|>1` (`RTA_Cache.cpp:358`); `AssertSingleChangeInvariant` (debug) re-checks; `AdoptChampion` on every strict-improvement so the next variation stays `|diff|≤1` (a frozen champion would drift to `|diff|>1`). **Recommendation:** state as a **stated property backed by a structural invariant** (enforced by construction: cache throws on violation, descent re-adopts champion each step, serialized queue walks one task at a time), as a 3-line "Proposition (single-change invariant)" citing the enforcement — not a full theorem/proof. The complexity claim (RTA-cache `O(N·O_RTA)` per move) *depends* on it → state explicitly.

## 2. Time-limit (config) optimization — coordinate descent over the TL grid

TL optimizer `OptimizePA_Incre_with_TimeLimits` extends `OptimizePA_Incre`. A task's TL λ_i caps its ET (smaller TL = less ET/interference but lower perf coefficient). `UpdateExtDistBasedOnTimeLimit` bakes a TL vector into the DAG (replace `execution_time_dist` with point mass at TL, −1=unchanged). Candidate TLs per task = `timePerformancePairs` grid (`RecordTimeLimitOptions`; no pairs → `{-1}`-only sentinel). **Coordinate descent** (`WalkOneTaskWithTimeLimitOptions`): per task, unidirectional outward walk from baseline option index (`FindTimeLimitOptionIndex`), step `step` (−1/+1) to grid boundary; each step set `time_limits[task_idx]=opts[i]`, eval. **Adoption** `IsBetterTimeLimitOption`: adopt on strictly-greater SP (beyond `ApproxEqualSP`); on an approx-equal *tie* adopt only when stepping **downward** (`step<0`) — tie-break prefers smaller (tighter) TL. `WouldBeatIncumbent` mirrors at commit (tie beats iff challenger's total TL sum strictly smaller). **Patience, not radius:** on a non-improving step, `patience==0`→break (strict), else `--patience` and keep stepping past the dip; patience is a **total** non-improvement budget, not reset on improvement (incremental `patience=0` strict — SP-vs-TL ~unimodal when PA warm-started; reopt `patience=1` tolerates one dip — from-scratch PA can be non-unimodal). **Two passes per task** (`OptimizeOneTaskWithTimeLimit`): backward then forward from same origin; eval lambda routes each trial TL through `OptimizeIncreSingleTask` (sub-incremental: re-score carried PA + 1D PA re-search); after each task `starting_time_limits=ReconstructTimeLimitVecFromResOpt()` syncs to adopted champion. **Task ordering:** serialized E+L queue (`BuildSerializedTaskQueue`) sorts weight desc (stable). **Entry points:** `OptimizeIncre_w_TL` (inc, warm-started) + `ReOptimizePeriodic` (from-scratch compare-and-keep) both delegate to `RunIntervalDescent` (the ONE shared descent body); `Optimize_w_TL_ScratchOrIncre` dispatches — every `ReoptimizationPeriod`-th (=10) call takes reopt, else incremental; `count==0` bootstraps via reopt. **Complexity M^N→O(M·N):** BF over TL (`EnumeratePA_with_TimeLimits`) recurses every task's full TL set → `M^N` combos, each running a full PA search; coordinate descent: per task ≤M grid options (fewer — patience stops early), N tasks → **O(M·N)** TL evals per interval, each one `OptimizeIncreSingleTask` (≤1-task RTA-cache patch + 1D PA re-search), NOT a full PA search. So the drop **is confirmed by code**, but the mechanism is **patience-bounded coordinate descent over the full grid**, NOT a δ-radius local window (the draft's framing — §4). **Why:** TL trades safety vs perf; full grid `M^N`; coordinate descent optimizes one task's TL at a time (others fixed), exploiting SP ~unimodal in each task's TL when PA held. Patience (not radius) bounds the walk: `patience=0` safe under unimodal, `patience=1` hedges non-unimodal reopt.

## 3. Env-task reframing — one merged E+L queue

**Section-8 conceptual reframing:** TL-optimizable tasks = a *special kind of env-dependent task*, unifying TL-flex + env-change handling under **one incremental mechanism** (the serialized E+L queue). **Type-E (env-changed):** `FindEnvTaskWithDifferentEt` = `FindTaskWithDifferentEt` **minus** TL-flexible tasks (`FindTasksWithFlexibleTimeLimits` — TL-flexible iff non-empty `timePerformancePairs`). Filter needed because `FiniteDist::operator!=` is 10%-relative approx_equal and a TL-flexible task's dist is built from raw YAML mu/min/max (no TL override) → can compare unequal across intervals for TL-induced (not env) reasons. **Type-L (TL-flexible):** `CollectTLFlexibleTaskIds` — IDs whose option set is NOT the `{-1}`-only sentinel. **Merged queue:** `BuildSerializedTaskQueue` concatenates Type-E + Type-L, sorts weight desc (stable). E/L must be **disjoint** (TL-flexible tasks have no env dependence by generator design); a task in both → `CoutError` (contract violation, not silent pick). **One dispatch** (`WalkSerializedTaskQueue`): Type-E→`OptimizeIncreSingleTask` re-search at committed TL (no TL walk); Type-L→`OptimizeOneTaskWithTimeLimit` (the TL walk, each step `OptimizeIncreSingleTask`). Each step adopts into `res_opt_` → next step's challenger sees new champion, diff flags only the walked task (`|diff|≤1`). **Why:** unifies TL-flex + ET-change handling — both reduce to "one task's effective ET differs from the champion" (Type-E: env moved ET; Type-L: trial TL moved ET). Routing both through `OptimizeIncreSingleTask` (the ≤1-task RTA-cache patch) keeps the cache's single-change invariant for the whole walk; online cost bounded by *#changed+TL-flexible tasks*, not N or M. The paper must state: a TL-optimizable task is a special kind of env-dependent task.

## 4. Draft drift — `‖λ−λ^(k)‖≤δ` / "3 candidates" is STALE

**Finding:** the draft's `eq: incremental_configuration` (`section8_task_config_opt.tex:23`, `\|\boldsymbol{\lambda}-\boldsymbol{\lambda}^{(k)}\|\leq\delta`) and section9 ("δ such that the optimization only considers 3 candidates") describe a **radius-bounded local window** the production code **no longer implements**. Evidence: (1) `parameters.yaml:17-18`: *"The walk is not radius-capped — a tie-break or strictly-better option beyond the old radius wall is reachable."* (2) Production walk `WalkOneTaskWithTimeLimitOptions` steps the **full** per-task option set, bounded by `patience`, not δ. (3) `RecordCloseTimeLimitOptions` (the radius-bounded builder using `Find_Close_ExecutionTime`+`radius`) survives **only in tests** (`tests/testBF_w_TL.cpp`, `tests/testIncreOpt_w_TL.cpp`) — no production caller. (4) Production TL option set is `RecordTimeLimitOptions` (`OptimizeSP_TL_BF.cpp:19-35`) = the **full** `timePerformancePairs` grid (no radius window). **Implication:** section8 `eq: incremental_configuration` + "δ/3 candidates" must be **rewritten** to the patience-bounded outward walk over the full grid: the constraint is not `‖λ−λ^(k)‖≤δ` but "step outward from λ^(k) over the grid until `patience` consecutive non-improving evals." The "3 candidates"/"2 potential candidates: 200, 300" example is likewise stale. Flag for PW.1.4 + PW.3 §8.

## 5. DM seed + important-first group lock (P0.9/P0.10)

Seed PA for reopt/incremental bootstrap = `DeadlineMonotonicPriorityVec`: DM (shorter deadline = higher pri) because deadlines are constrained (`deadline=period*U(0.5,1.0)`), with **important-first group lock** — every important task ranks above every non-important (`if (ta.is_important != tb.is_important) return ta.is_important`), DM-ordered within group, ties avg-ET asc. Shared shape behind this + BF DM modes lives in `BuildPriorityPlan` (`PriorityBuilders.cpp:22-49`), dispatched by `PriorityBuilderConfig{SortKey,GroupLock,TimeLimitPolicy}` (`PriorityBuilders.h:24-28`): `SortKey::kDeadline`=DM, `kPeriod`=RM; `GroupLock::kImportantFirst`=lock, `kNone`=plain sorted. RM-Fast fallback (`RateMonotonicFastGroupLocked`) uses same builder with `kPeriod`+`kImportantFirst` (owned by PW.1.3). `DEADLINE_MODE=implicit` = config-level deadline semantics (memory: config-tuning `7c8748c0`).
